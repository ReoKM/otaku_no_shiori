# release-check — リリース判定

## 役割1行

チェックリストを1項目ずつ実際に確認し、リリース可否を判定する。

## 成果物

判定結果レポート(下記フォーマット)。重大な問題はGitHub Issue化。

## 完了条件

- [ ] 全項目が「確認済み◯ / 問題あり× / 対象外-」のいずれかになっている
- [ ] ×の項目すべてにIssueがある
- [ ] 判定(リリース可 / 不可)と理由が明示されている

## チェックリスト

### 品質
- [ ] CI(lint / tsc / ユニットテスト)が `main` で全部通る
- [ ] E2E主要フロー(しおり作成→持ち物チェック→共有画像生成)が通る
- [ ] 375px幅で主要画面(S1〜S6)が崩れない
- [ ] リロードでゲストデータが消えない
- [ ] オフラインで旅程・持ち物・TODOが閲覧できる

### セキュリティ・コスト
- [ ] 全テーブルにRLSが有効(子テーブル含む)
- [ ] Storageバケットのサイズ・MIME制限が有効
- [ ] 秘密情報がリポジトリに含まれない
- [ ] 写真上限が環境変数でのみ変更可能(ユーザー設定に露出していない)

### 計測・収益
- [ ] GA4が動いている(`via=share` の識別を含む)
- [ ] 広告枠が表示される(審査前は自社告知)

### 公開要件
- [ ] 利用規約・プライバシーポリシーが公開されている
- [ ] 運営者情報・問い合わせ手段がある
- [ ] OGP(タイトル・説明・画像)が設定されている

## 手順

1. チェックリストを上から順に**実際に確認する**(コマンド実行・画面確認)。記憶で埋めない
2. ×の項目は1件ずつIssueを作る(再現手順付き)
3. 判定する: セキュリティ・コスト分類に×が1つでもあれば**リリース不可**。他分類の×はPMと重要度を協議
4. 結果レポートを出力する

## 結果レポートのフォーマット

```markdown
## release-check 結果 YYYY-MM-DD

判定: リリース不可

| 分類 | 結果 |
|------|------|
| 品質 | ◯◯◯×◯(E2E共有画像で失敗 → Issue #30) |
| セキュリティ・コスト | 全◯ |
| 計測・収益 | 全◯ |
| 公開要件 | ◯◯×(OGP画像未設定 → Issue #31) |

不可の理由: E2E失敗(コア機能)。Issue #30 解消後に再実行する。
```

## やらないこと

- 確認せずに◯を付けない
- ×を残したまま「条件付きリリース可」にしない(判断はPM・オーナーへ)
- 修正の実装(Issue化まで)

## 出力例

入力: `/release-check`
出力: 16項目確認、×2件(Issue #30, #31 作成)、判定「リリース不可」、上記フォーマットのレポート。
