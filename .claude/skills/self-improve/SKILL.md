# self-improve — エージェント定義の自己改善

## 役割1行

観察された失敗から定義文の欠陥を特定し、`.claude/` を小さく直す。

## 成果物

- 改善PR(`.claude/` 配下、3ファイル以内)
- 改善ログ: `docs/logs/self_improve/YYYY-MM-DD.md`

## 完了条件

- [ ] 監査対象・見つけた問題・原因・対応が改善ログに記録されている
- [ ] すべての修正が観察された失敗に紐づいている
- [ ] 修正後の定義が `docs/05_agent_team.md` のライティング規約を満たす

## 手順

1. 直近1週間の成果物をサンプリングする(目安: PR3件、レポート/カレンダー各1件、レビューコメント2件)
2. 各成果物を担当エージェント定義(`.claude/agents/`)の「完了条件」と照合し、満たす/一部/満たさない で採点する
3. 「満たさない」ごとに原因を**定義文の欠陥**として1文で言語化する
   - 良い例: 「手順に既存コードの探索が無いため重複実装が起きた」
   - 悪い例: 「エージェントの能力不足」(定義で防げる形に言い換える)
4. 最小限の修正案を作る(該当の手順・表・例だけを直す。丸ごと書き直さない)
5. 修正後の文面をライティング規約チェックリスト(`.claude/agents/self-improver.md` 参照)で確認する
6. 改善PRと改善ログを作る

## 改善ログのフォーマット

```markdown
# 自己改善ログ YYYY-MM-DD

## 監査対象
- PR #12(frontend-dev)/ docs/reports/2026-W30.md(analytics-growth)/ …

## 見つけた問題と原因
| 問題 | 原因(定義の欠陥) | 対応 |
|------|-------------------|------|
| 重複実装が2PRで発生 | frontend-dev手順の探索指示が弱い | 手順4を具体化 |

## 修正したファイル
- .claude/agents/frontend-dev.md
```

## やらないこと

- エージェントの追加・削除・役割変更(PM経由でオーナー承認)
- 1PRで4ファイル以上の修正
- `docs/` の仕様本体の書き換え(仕様の問題は `/spec-sync` へ)
- 失敗の観察なしの書き換え

## 出力例

入力: `/self-improve`
出力: 監査6件、問題2件特定、改善PR1件(2ファイル)、`docs/logs/self_improve/2026-07-14.md` 作成。
