# spec-sync — 仕様と実装の同期

## 役割1行

「docs/ を読めば現状が正しく分かる」状態を維持する。

## 成果物

- 差分レポート(このスキルの実行結果として出力)
- docs更新PR(差分があった場合)

## 完了条件

- [ ] 下の照合表の全項目を確認した
- [ ] 差分が「仕様が古い」「実装が仕様違反」のどちらかに分類されている
- [ ] 「仕様が古い」ものはdocs更新PRを作った。「実装が仕様違反」はIssue化した

## 手順

1. `docs/01_service_spec.md` の機能一覧(F1〜F10)と実装(`src/`)を突き合わせる
2. `docs/03_tech_stack.md` のデータモデルと `supabase/migrations/` を突き合わせる
3. 差分を1件ずつ分類する:
   - **仕様が古い**(実装が正・オーナー承認済みの変更): docsを直すPRを作る
   - **実装が仕様違反**(仕様が正): 修正Issueを作り担当エージェントに割り当てる
   - **判断不能**: PMのオーナー判断リストに回す
4. docs更新PRは変更理由を各修正箇所のコミットメッセージに書く

## 照合表

| 照合対象 | 見るもの |
|----------|----------|
| 機能(F1〜F10) | `docs/01_service_spec.md` ↔ `src/app/` の画面・API |
| 画面(S1〜S6) | `docs/design/screens/` ↔ 実装済みルート |
| データモデル | `docs/03_tech_stack.md` ↔ `supabase/migrations/` |
| テンプレ | `docs/01_service_spec.md` のテンプレ仕様 ↔ `src/templates/` |
| ロードマップ進捗 | `docs/02_roadmap.md` のマイルストーン ↔ 実装状況 |

## 差分レポートのフォーマット

```markdown
## spec-sync 結果 YYYY-MM-DD

| # | 差分 | 分類 | 対応 |
|---|------|------|------|
| 1 | 写真上限が仕様20枚・実装30枚 | 実装が仕様違反 | Issue #21 作成(backend-dev) |
| 2 | 持ち物テンプレが仕様3種・実装4種(承認済み追加) | 仕様が古い | docs更新PR #22 |
```

## やらないこと

- 実装コードの修正(Issue化まで)
- オーナー承認の記録がない変更を「仕様が古い」に分類しない(判断不能に回す)
- ロードマップの書き換え(進捗チェックの更新のみ可)

## 出力例

入力: `/spec-sync`
出力: 差分3件検出。仕様が古い1件→docs更新PR作成、実装が仕様違反1件→Issue作成、判断不能1件→PMへ。上記フォーマットのレポートを出力。
