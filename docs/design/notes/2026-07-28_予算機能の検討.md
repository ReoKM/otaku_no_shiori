このファイルは**意思決定の記録**であり、仕様の正ではない。採用が決まった内容は `docs/01_service_spec.md` と `docs/02_roadmap.md` に反映してから実装する。

## 結論(先に3行)

1. **予算機能は「条件付き採用」。ただし今は作らない。** まず1日の検証作業でニーズを測り、4週間後に採否を決める

3. **推し活スタイル登録によるレコメンド(アフィリエイト)は見送り。** 収益は月0〜1,000円(推定)の一方、法務・プライバシー・UX方針の3つを同時に崩す

## 前提の訂正: 「3人に2人」は根拠にしない

メモにあった「AIを使った旅行プラン、3人に2人が今年の夏休みでやっている」(TV番組)は、**企画の根拠として採用しない**。理由は3つ。

1. 出典・母集団・n数・設問文が不明。「AIを使った旅行プラン」の定義も不明
2. 対象が一般旅行者であり、本サービスのターゲット(オタクの遠征・聖地巡礼)ではない。`docs/00_vision.md` は「汎用旅行プランナー」を非スコープとしており、一般旅行の統計を根拠に機能を足すと非スコープ側へ寄る
3. そもそも論点がずれる。旅行プラン生成AIに予算を入れるのは**AIに制約条件を渡すため**であり、予算を管理したいからとは限らない。本サービスに現状AI生成は無い(Phase 3)ので動機が移植できない

この数字は「オーナーの関心が強いテーマである」証拠としてのみ扱う。**代わりに使える一次情報**は次のとおり:

| 根拠 | 性質 |
|---|---|
| 既存TODOテンプレの「遠征資金の準備」(`src/templates/todo-templates.ts`) | 仕様策定時に自分たちで「遠征準備に金の段取りがある」と判断済み。**チェック率を計測すれば実データになる** |
| ペルソナ2(初遠征オタク)の課題「何を予約すればいいか分からない」(`docs/00_vision.md`) | 文書化済みの一次仮説 |
| X上の実投稿(「遠征費」「参戦費用」で50件読む) | 既にスプレッドシートや家計簿アプリで満たされているなら、機能の必要性は下がる |
| 検索需要(Googleサジェスト・関連検索・キーワードプランナー) | 無料で確認可能 |

## A. 機能としての評価

### 北極星への効き方: 弱い

北極星は「作成され、完了(遠征実施)まで使われたしおりの数」(`docs/00_vision.md`)。これを伸ばすのは**当日利用**(持ち物チェック・旅程・PWA)であり、予算は**準備期に1回使って終わる機能**で当日の起動理由を作らない。

効きうる経路は2本あるが、いずれも未検証の仮説:

1. 準備期の投入コストが増える → しおりへの愛着が上がり当日も開く(間接・弱い)
2. 「グッズにいくら残せるか」を**当日その場で見る**なら当日利用に効く。ただしそれは実支出記録=家計簿機能であり、入力負担が重く離脱要因になりやすい

**「AIが宿代を提案する」ことは、上のどちらの経路にも寄与しない。** 効くとすれば「残額が見える」ことのほう。ここは切り分ける。

### フェーズ: Phase 2(Phase 1には入れない)

- Phase 1(W3公開)は F8/F10/F9/規約/計測が未完で、F8はオーナー作業でブロック中。追加は公開遅延に直結する
- 仕様上も予算は F1〜F10 に無く、`docs/01_service_spec.md` の「迷ったら削る」思想に反する
- Phase 3 に送るほど大きくもない。Phase 2 で小さく試すのが妥当

### 最小で価値が出る形

- しおり単位の「予算総額」1つ + 費目行(名前+金額)の手入力 + **合計と残額**の表示 + メモ
- 費目は遠征タイプ別プリセット(交通/宿/グッズ/食事/予備費)で投入。持ち物テンプレと同じ仕組みを流用し、「AI試算の代わり」をテンプレで満たす
- **AIによる金額提案はしない。** AI API費が発生し、Phase 3のクレジット課金基盤とセットで設計すべきものを単独先行させると、原価回収の設計が無いまま出費が始まる
- **実支出の記録・レシート入力・当日精算はやらない。** 北極星への寄与が未検証のまま入力負担だけが増える

## B. 配置の評価: タブ5個は不採用

`src/components/shiori-detail/TabBar.tsx` の実装値(`grid-cols-4` / 高さ48px / `text-[15px]` / 字間0.02em)からの実測。

| 項目 | 4タブ(現行) | 5タブ |
|---|---|---|
| 1タブの幅(375px) | 93.75px | 75.0px |
| 最長ラベル「やること」の実幅 | 61.2px | 61.2px |
| ラベル左右の余白(片側) | 16.3px | 6.9px |
| **隣接ラベル間の距離** | 32.6px | **13.8px** |
| タップ領域 | 93.75×48px | 75×48px |

**破綻するのはタップ領域ではなく可読性。** タップは5タブでも44pxを満たす(75px)。問題は隣接ラベル間13.8pxが文字高15pxを下回り、「やること|旅程|記録|予算」が1本の文字列として読めてしまうこと。

5タブに収めるにはラベルを3文字以内((75−24)÷15.3=3.3字)にする必要があり、既存の「やること」を改名しなければならない。320px幅端末では1タブ64pxとなり、「やること」61.2pxに対し片側余白1.4pxで即破綻する。

### 配置候補の比較

| 案 | 概要 | 判断 |
|---|---|---|
| A | タブを5個に増やす | **不採用**(上記の数値) |
| B | 旅程タブ内のセグメントに追加 | 不採用。旅程は**当日利用の中心**で、準備期の予算を同居させると「当日タブ」の性格が濁る |
| C | ヘッダー配下の共通「概要」領域 | 不採用。当日タブの縦スペースを常時奪い、スクロール量削減の方針に逆行 |
| D | やることタブ内のセクション(縦積み) | 不採用。やることリストの前後に予算カードが挟まりスクロールが増える |
| **E** | **やることタブ内のセグメント切替(やること / 予算)** | **採用** |
| F | S2しおり作成の入力項目にし、詳細では読み取り専用 | 不採用。予算は作成後に何度も見直す情報。S2の入力項目が増え離脱要因になる |

### 採用案 E の理由

1. 予算はF3テンプレ「遠征資金の準備」と同じ**準備期タスク**で、やることタブと利用フェーズが一致する
2. タブ4個を維持したまま、**当日タブ(持ち物・旅程)には一切触れない**
3. F5(スポット)で採用済みの2分割セグメントをそのまま流用でき、**新規UIパターン・新規トークンがゼロ**

画面仕様の詳細は `docs/design/screens/S3b2_予算.md` を参照(このPRで作成済み。オーナー承認前のため仕様の正ではない旨を明記してある)。

## C. レコメンド/アフィリエイトの評価: 見送り

### 収益の推定(すべて推定・実測ゼロ)

前提: 月3,000PV(Phase 1 KPI からの逆算)/ クリック率1% / 購入率1% / 料率2% / 客単価5万円

- 月間クリック 30 → 月間成約 0.3件 → **月間収益 約300円(推定)**

楽天のように1件あたり上限額がある場合はこれ以下。**桁で見て月0〜1,000円**で、ドメイン代(月約150円)を少し超える程度。実装・審査・法務対応の工数に見合わない。

### 審査の壁

- Amazonアソシエイトは一般に登録後180日以内の一定件数の適格販売が必要とされ、上の推定(月0.3件)では**期間内に到達せず審査に落ちる公算が高い**
- ASP全般が「コンテンツ量」を審査観点にする。現状はLP1枚+ツール画面で、`docs/04_growth_monetization.md` にあるAdSense審査の懸念とまったく同じ弱点

### 既存方針との衝突(3点)

1. **F9の広告枠は2箇所で実用画面には置かない**方針。「このタイミングでレンズいかがですか」は遠征準備中=実用画面に出す提案で、正面から反する
2. **推し活スタイルの事前登録は個人プロファイルの収集**。プライバシーポリシー改定が必要で、CLAUDE.md の「権利・法務」= オーナー判断領域
3. **ステマ規制(景表法)対応**が必須。広告であることを明示する必要があり、明示すると「運営のおすすめ」の説得力は落ちる

`docs/04_growth_monetization.md` ではアフィリエイトは段階3「(検討)」・Phase 2以降・優先度低め。オーナー案はこれを段階1より前に持ってくることになり、**ロードマップ変更に当たる**。

**再検討の条件: 月間1万PVの実測。** そこで初めて月数千円の桁に乗る可能性が出る。

## 決定した進め方

**いま実装はしない。1日の検証作業を走らせ、4週間後に採否を決める。** 検証コストは実装より1桁小さく、外した場合の損失も小さい。

### ステップ1: 計測の土台を作る(実装0.5日)

現状 `NEXT_PUBLIC_GA_ID` が未設定で、GA4は `gtag('config')` のみ。カスタムイベントの送信口が存在せず、**北極星は定義はあるが計測不能**の状態。

- `src/lib/analytics.ts` にGA4イベント送信ラッパーを作る(`gaId` 未設定時はno-op)
- しおりごとにランダムUUID `shiori_key` を発行し、全イベントに付ける。これが無いと「予算を入れた人が最後まで使ったか」が測れない
- 個人情報・しおり名・推し名・ジャンル名・**金額そのものは送らない**(対象がセンシティブなため)

| イベント名 | タイミング | パラメータ |
|---|---|---|
| `shiori_create` | しおり作成完了 | `shiori_key`, `is_guest` |
| `todo_check` | テンプレTODOのチェック | `shiori_key`, `label_key`(テンプレ固定値のみ) |
| `photo_add` | 写真ログ追加 | `shiori_key` |
| `share_image_generate` | F7生成完了 | `shiori_key`, `template_id` |

### ステップ2: 需要を測る(実装ゼロ・0.5日)

公式Xに「遠征予算の内訳テンプレ画像(グッズ/宿/交通/食事/予備費)」を1本投稿する。`docs/04_growth_monetization.md` の「遠征お役立ちコンテンツ」の型にそのまま乗るので、新しい枠組みを作らずに需要が測れる。

判断に使う数字: **同週の他投稿(持ち物チェックリスト等)に対する保存数の比**。

### ステップ3: 4週間後に判定

**母数がしおり作成30冊に達するまで、どの数字でも判断しない。** 実績ゼロの現状、10冊での「入力率20%」は2冊のこと。ノイズで機能を足したり畳んだりしないため、母数の下限を先に固定する。

| 判定 | ライン | 結果 |
|---|---|---|
| TODO「遠征資金の準備」のチェック率 | テンプレ6項目の平均を**下回る** | 予算機能は作らない |
| X投稿の保存数 | 同週の他投稿の**半分未満** | 記事・機能とも見送り |

両方を上回った場合のみ、Phase 2 で最小形を実装する。

### 実装が決まった場合の撤退ライン(先に決めておく)

| タイミング | ライン | 対応 |
|---|---|---|
| 公開4週間後 | `budget_set` / `shiori_create` が15%未満 | 縮小(導線を1段下げる)。改修で粘らない |
| 公開4週間後 | 同 8%未満 | 撤去 |
| 公開8週間後 | 予算ありの完了率 − 予算なしの完了率 ≤ 0pt | 北極星に無関係と判断し、以後リソースを割かない |

**最上位の撤退ライン**は `docs/02_roadmap.md` に既にある: 公開後8週でしおり作成数が2桁に届かなければターゲット・訴求の再設計に戻る。この状態に入ったら**予算機能の議論自体を止める**。機能追加で解決しようとしない。

## 実装する場合のデータ設計(先行検討済み)

採否が決まってから着手するが、設計は済ませてある。

- `shiori.budget_total integer`(NULL=未設定。0と区別するためDEFAULTを付けない)
- 子テーブル `budget_items`(`label` / `amount` / `memo` / `sort_order`)。既存の `packing_items` / `todos` と**完全に同じ形**で、RLS・ゲスト保存・移行のパターンを全部流用できる
- RLSは親 `shiori.user_id` を参照する `EXISTS` ポリシー4本(CLAUDE.md 必須要件)
- 金額は **`integer`(円)**。円に補助単位は無く、`numeric` は丸め議論と型変換を持ち込むだけで利点がない
- 合計・残額はDBに持たず、1クエリの結果をクライアントで合算する(集計トリガー・キャッシュ列を作らない)
- IndexedDB は `DB_VERSION` 2→3。`deleteShiori` のトランザクションに `budget_items` を足す(漏れると孤児データになる)

**採用しなかった案**: 単一JSON列(行単位の更新が read-modify-write になり同時編集で壊れる。DB側で型・件数の検証ができない) / 既存 `packing_items` に金額列を足して兼用(意味が違うものを混ぜると判別列とフィルタが全画面に伝播し、持ち物削除で予算が消える事故が起きる)
